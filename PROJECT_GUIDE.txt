MARINE-INATURALIST — GUIDE COMPLET D'ARCHITECTURE ET DE FONCTIONNEMENT

1. POURQUOI CETTE ARCHITECTURE MODULAIRE ?
--------------------------------------------------------------------------------
Dans un notebook monolithique, le chargement des données, la définition des
réseaux, la boucle d'entraînement et les chemins locaux sont mélangés. Cette
organisation fonctionne pour un prototype rapide, mais échoue dès que l'on
passe d'un PC Windows (NVIDIA RTX) à un MacBook (Apple Silicon MPS) ou à un
cluster Linux multi-GPU (DDP via torchrun).

Le dépôt sépare strictement les responsabilités en trois couches :
  - configs/  : source unique de vérité pour les chemins et hyperparamètres.
  - src/      : bibliothèque Python réutilisable organisée par domaine métier.
  - scripts/  : points d'entrée en ligne de commande légers assemblant src/.

Exécutez toujours les scripts depuis la racine du dépôt via `python -m ...`
afin que Python résolve les imports `src.*` de manière identique sur tous les OS.


2. CONFIGURATION ET INFRASTRUCTURE (configs/ & src/utils/)
--------------------------------------------------------------------------------
[configs/default.yaml & configs/beefy_cnn.yaml]
  - Centralisent tous les répertoires, paramètres du dataset, dimensions des
    modèles et hyperparamètres d'optimisation.

[src/utils/config.py]
  - Charge le fichier YAML et applique la variable d'environnement
    MARINE_DATA_ROOT ou l'argument CLI --data-root pour relocaliser d'un seul
    coup l'ensemble des sous-dossiers (images, manifests, checkpoints, logs).

[src/utils/device.py]
  - Sélectionne automatiquement le matériel le plus performant disponible :
      1. Cluster multi-GPU (torchrun -> DistributedDataParallel / NCCL)
      2. GPU NVIDIA local (cuda -> RTX avec précision mixte FP16/AMP)
      3. Puces Apple Silicon (mps -> GPU MacBook)
      4. Repli automatique sur cpu
  - Aucun appel codé en dur à `.cuda()` n'existe dans le code source.

[src/utils/checkpoint.py]
  - Sauvegarde l'état complet à chaque epoch (<modele>_last.pt) ainsi que le
    meilleur modèle selon le Macro-F1 de validation (<modele>_best.pt).
  - Écriture atomique : écriture dans un fichier temporaire `.tmp` puis
    renommage instantané via `os.replace()`, évitant toute corruption en cas
    d'interruption (Ctrl+C ou fin de quota Slurm sur cluster).
  - Sauvegarde les poids du modèle, les moments AdamW, le pas du scheduler,
    l'état du GradScaler AMP et les graines aléatoires Python/NumPy/PyTorch.

[src/utils/logger.py & src/utils/visualize.py]
  - `logger.py` alimente `logs/metrics.csv` à chaque fin d'epoch et consigne
    les traces complètes d'exception dans `logs/crash.log`.
  - `visualize.py` génère la planche graphique `logs/training_curves.png`
    en mode sans écran (`Agg`) pour fonctionner sur serveur Linux headless.


3. PIPELINE DE DONNÉES ET CORRECTION DU REDIMENSIONNEMENT (src/data/)
--------------------------------------------------------------------------------
[src/data/transforms.py]
  - Utilise Albumentations pour transformer des tableaux NumPy uint8 (H, W, C)
    en tenseurs PyTorch float32 normalisés de dimension (3, 224, 224).
  - Correction du redimensionnement (Warp vs Crop) :
      * Auparavant, `SmallestMaxSize(256)` suivi de `RandomCrop(224)` ou
        `CenterCrop(224)` tronquait les spécimens allongés (anguilles, raies,
        coraux ramifiés, cétacés) ou situés en bordure de cadre.
      * Désormais, `build_train()` et `build_val()` utilisent `A.Resize(224, 224)`
        (transformation de type warp) afin de conserver 100 % de l'organisme
        marin dans le champ de vision du réseau.

[src/data/dataset.py]
  - `SampleRecord` (`@dataclass(frozen=True, slots=True)`) réduit fortement
    l'empreinte mémoire RAM lors du passage à l'échelle sur plusieurs millions
    d'images.
  - Résolution portable des chemins : si `train.csv` ou `val.csv` a été créé
    sous Windows puis transféré sur un cluster Linux, `MarineSpeciesDataset`
    retrouve automatiquement les images dans `<data_root>/images/<espece>/`.
  - Supporte également la lecture directe depuis l'archive binaire contiguë
    `dataset.bin` (générée par `scripts/01b_pack_shard.py`).
  - Sur Windows et macOS, les workers DataLoader utilisent `spawn` : tous les
    scripts protègent donc leur point d'entrée avec `if __name__ == "__main__":`.


4. ARCHITECTURES ENTRAÎNÉES DEPUIS ZÉRO (src/models/)
--------------------------------------------------------------------------------
[src/models/cnn_rnn.py — model.name: "cnn_rnn"]
  - Architecture hybride combinant extraction locale et balayage séquentiel :
      1. Entrée : (B, 3, 224, 224)
      2. Encodeur CNN à 5 étages (Conv2d -> BatchNorm2d -> ReLU -> MaxPool2d) :
         224 -> 112 -> 56 -> 28 -> 14 -> 7, canaux 3 -> 32 -> 64 -> 128 -> 256 -> 512.
      3. Conversion spatiale -> séquence : (B, 512, 7, 7) -> (B, 49, 512) + LayerNorm.
      4. RNN bidirectionnel à 2 couches (RNN tanh, GRU ou LSTM) -> (B, 49, 512).
      5. Moyenne globale sur les 49 jetons + Dropout + couche linéaire -> (B, 2185).

[src/models/beefy_cnn.py — model.name: "convolutional_resnet"]
  - Architecture purement convolutive inspirée de ConvNeXt :
      1. Stem patchify 4x4 (stride 4) -> (B, 96, 56, 56).
      2. 4 étages hiérarchiques (blocs 3, 3, 9, 3) avec convolutions depthwise 7x7,
         LayerNorm2d, expansion 4x avec activation GELU et facteur résiduel LayerScale.
      3. Pooling moyen global + LayerNorm + Dropout + tête linéaire -> (B, 2185).


5. MOTEUR D'ENTRAÎNEMENT ET SCRIPTS CLI (src/training/ & scripts/)
--------------------------------------------------------------------------------
- `src/training/metrics.py` & `src/training/trainer.py` :
    * Calcul exact de l'exactitude Top-1 et du Macro-F1 (moyenne équilibrée sur
      les 2 185 espèces), synchronisé par `all_reduce` en mode multi-GPU DDP.
    * Précision mixte AMP + écriture mémoire `channels_last` + `CudaPrefetcher`.
    * Écrêtage des gradients (`max_grad_norm`) et protection contre les lots NaN/Inf.

- Aide-mémoire des commandes :
    * Audit des clés :
        python -m scripts.00_inspecter_cles --data-root <dossier_donnees>
    * Téléchargement et découpage stratifié :
        python -m scripts.01_telecharger_et_couper --data-root <dossier_donnees>
    * Compactage binaire optionnel (cluster) :
        python -m scripts.01b_pack_shard --data-root <dossier_donnees>
    * Entraînement mono-GPU / Mac / CPU :
        python -m scripts.02_train --config configs/default.yaml --data-root <dossier_donnees>
    * Reprise après interruption :
        python -m scripts.02_train --config configs/default.yaml --resume <chemin/vers/*_last.pt>
    * Entraînement distribué multi-GPU (Linux cluster) :
        torchrun --nproc_per_node=4 -m scripts.02_train --config configs/beefy_cnn.yaml --data-root <dossier_donnees>
    * Évaluation validation et prédiction test :
        python -m scripts.03_evaluate --mode val --data-root <dossier_donnees>
        python -m scripts.03_evaluate --mode test --data-root <dossier_donnees> --test-dir <dossier_test>


6. TESTS, LINT ET INTÉGRATION CONTINUE (tests/, .github/workflows/, pyproject.toml)
--------------------------------------------------------------------------------
[Installation développeur]
  python -m venv .venv && source .venv/bin/activate
  pip install torch torchvision
  pip install -e ".[dev]"        (dépendances du projet + pytest + ruff)

[tests/]
  - conftest.py          : génère un mini-jeu de données factice (3 espèces, 18 images
                           JPEG minuscules, manifestes train/val) dans un dossier temporaire.
  - test_metrics.py      : Top-1 / Macro-F1 vérifiés sur un cas calculé à la main.
  - test_models.py       : registre, formes de sortie (RNN/GRU/LSTM, ConvNeXt), erreurs.
  - test_config.py       : chaque YAML se charge, désigne un modèle enregistré ;
                           --data-root et MARINE_DATA_ROOT relocalisent tous les chemins.
  - test_dataset.py      : lecture disque et lecture via dataset.bin donnent les mêmes pixels.
  - test_smoke_train.py  : 1 epoch complète sur CPU pour default.yaml et beefy_cnn.yaml
                           (--batch-size 4 car drop_last=True : un lot trop grand donnerait
                           zéro itération). Marqué "slow".
  Commandes : pytest | pytest -m "not slow" | ruff check .

[Limites volontaires]
  - Les runners GitHub n'ont pas de GPU : DDP/NCCL, AMP et CudaPrefetcher ne sont PAS testés
    par la CI. Ils se valident à la main sur le cluster.
  - ruff est configuré avec un jeu de règles minimal (E9 + F : erreurs de syntaxe, noms
    indéfinis, imports inutilisés) pour ne pas imposer de reformatage du code existant.

[.github/workflows/ci.yml]
  - Déclenché sur push vers main, sur toute Pull Request, et manuellement.
  - Job "lint" : ruff check.
  - Job "test" : Python 3.10 et 3.12, PyTorch CPU installé avant le projet (évite les Go de
    bibliothèques CUDA), puis pip install -e ".[dev]" et pytest.
  - Activation : le fichier doit être dans .github/workflows/ à la racine du dépôt ; il suffit
    de pousser sur GitHub, puis d'ouvrir l'onglet Actions. Pour rendre la CI obligatoire :
    Settings > Branches > règle de protection sur main > "Require status checks to pass".

[pyproject.toml]
  - [build-system] + [tool.setuptools.packages.find] : rendent `pip install -e .` possible
    (sans cela, setuptools refuse la structure plate src/ + scripts/ + configs/).
  - [project.optional-dependencies] dev : pytest, ruff.
  - [tool.pytest.ini_options] : testpaths, pythonpath (racine du dépôt), marqueur "slow".
  - [tool.ruff] : voir ci-dessus.
  - Remarque : "kaggle" et "six" figurent dans les dépendances mais aucun fichier Python
    du dépôt ne les importe actuellement.


7. DOCKER (Dockerfile, .dockerignore, .github/workflows/docker.yml) — OPTIONNEL
--------------------------------------------------------------------------------
  - Preuve de concept : le projet PEUT être conteneurisé, mais le workflow .venv reste la
    méthode de référence.
  - L'image (base pytorch/pytorch CUDA 12.4) ne contient que le code et les dépendances lues
    dans pyproject.toml. Données, checkpoints et logs sont dans un volume monté sur /data
    (MARINE_DATA_ROOT=/data).
  - Commandes :
      docker build -t marine-baseline .
      docker run --rm marine-baseline
      docker run --rm --gpus all --ipc=host -v <donnees>:/data marine-baseline \
          python -m scripts.02_train --config configs/default.yaml
      docker run --rm --gpus all --ipc=host -v <donnees>:/data marine-baseline \
          torchrun --nproc_per_node=4 -m scripts.02_train --config configs/beefy_cnn.yaml
  - --ipc=host (ou --shm-size) est indispensable avec num_workers > 0.
  - docker.yml : construit l'image et lance "--help" ; déclenché uniquement si Dockerfile,
    .dockerignore ou pyproject.toml changent dans une Pull Request, ou à la demande.
    Aucune publication sur un registre.
  - Non couvert : Apptainer/Singularity, publication d'image, clusters HPC.
